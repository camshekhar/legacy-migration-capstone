# Migration Decisions Log

This document records the design decisions behind this migration platform,
the rationale for thresholds and overrides, and the acknowledgments required
by the project brief, based on an actual end-to-end run against the seeded
legacy MySQL database.

## 1. Confidence Threshold

**Threshold: 0.80** (configurable via `CONFIDENCE_THRESHOLD` in `.env`).

Out of 30 total column mappings generated by `ai_mapper` (Gemini), 3 fell
below this threshold — exactly the columns the brief predicted would be
hardest: `billing_transactions.txn_st_cd`, `encounters.enc_st`, and
`patient_records.pat_st_cd`. All three are single-letter, undocumented
status codes with no reference lookup table, and all three sample sets
included corrupted/garbage values (`'?'`, `'!'`, stray characters) alongside
plausible-looking codes — exactly the ambiguity 0.80 was chosen to catch.

0.80 proved to be a reasonable cutoff in practice: it flagged the three
columns that genuinely needed a human domain expert, and did not flag
columns where Gemini's inference was reasonable (e.g. `pmt_mthd_cd`,
`prov_spec_cd`). It did, however, **miss** one real error —
`insurance_plans.plan_typ_cd` scored 0.85 (above threshold) but its
generated CASE statement silently drops the `'X'` (self-pay) code, mapping
every self-pay patient's plan type to `UNKNOWN` with no human ever seeing
it. See section 5 below — this is the more interesting finding of the two.

## 2. Sensitive Data Acknowledgment

The source schema contains at least one column that should be treated as
sensitive: `patient_records.ssn_enc`. As currently built, this platform
does **not** fully protect it: `agents/schema_profiler.py` samples raw
column values — including from `ssn_enc` — into `artifacts/schema_profile.json`,
which is then sent as-is to Gemini inside `ai_mapper`'s prompt. In this run
the sampled values were SHA-256-style hex strings (the seed data's stand-in
for "already encrypted at rest"), not real SSNs, which limited the exposure
in practice — but the pipeline as written would do the same thing with a
genuinely sensitive raw value if the source system stored one unencrypted.

**This is a known gap, not a solved problem.** A production version of this
pipeline should redact or hash any column flagged as sensitive (by name
pattern, e.g. `%ssn%`, `%dob%`, or by a data classification tag) before it
ever reaches `schema_profiler`'s sampling step, so the LLM never sees raw
sensitive values even in aggregate/sample form.

## 3. Human Overrides

Every mapping with confidence < 0.80 required human review before
`rule_generator` would include it in `transformation_rules.json`
(`agents/rule_generator.py` raises `UnapprovedMappingError` otherwise, and
this was verified directly — the pipeline genuinely paused and would not
proceed past `human_review_gate` without a resolved review, confirmed via
`audit/migration_audit_log.json`).

Review outcomes from this run:

- **`billing_transactions.txn_st_cd` -> `transaction_status_code`: OVERRIDDEN.**
  Gemini's initial mapping was `'W' -> 'WAITING'` and `'O' -> 'OTHER'`.
  Based on domain knowledge of legacy billing systems, the actual meanings
  are `W = Write-off` (debt abandoned as uncollectable) and
  `O = Outstanding` (payment still owed) — the opposite of what the AI's
  labels implied in terms of financial disposition. Corrected to:
  `CASE txn_st_cd WHEN 'P' THEN 'PAID' WHEN 'O' THEN 'OUTSTANDING' WHEN 'R' THEN 'REFUNDED' WHEN 'W' THEN 'WRITE_OFF' ELSE 'INVALID' END`.
  This is the clearest example in this run of an AI mapping that was
  plausible-sounding but functionally wrong — had it shipped, any report
  built on "outstanding receivables" would have been silently incorrect.

- **`encounters.enc_st` -> `encounter_status`: APPROVED as-is**, with one
  known imprecision accepted rather than corrected: Gemini mapped
  `'C' -> 'COMPLETED'`, where the more accurate legacy meaning is `Closed`
  (an administrative state, not necessarily a clinical outcome). This was
  judged low-stakes enough to accept rather than override, since "Completed"
  and "Closed" are close enough in practice for this encounter-status
  context — but it's flagged here explicitly rather than silently passed,
  since the same imprecision on a different column might not be acceptable.

- **`patient_records.pat_st_cd` -> `patient_status_code`: APPROVED as-is.**
  Gemini's fallback logic (`CASE WHEN pat_st_cd IN ('A','D','S','I','Z') THEN pat_st_cd ELSE 'UNKNOWN' END`)
  was judged reasonable: it passes through the plausible codes unchanged
  and correctly buckets garbage values (`'?'`, `'!'`) into `UNKNOWN` rather
  than guessing at their meaning.

All three decisions, their reviewer notes, and the exact prompt each
mapping came from are recorded in `audit/migration_audit_log.json`
(`human_review_decision` events) and traceable in LangFuse via each
mapping's `prompt_id` in `artifacts/mappings.json`.

## 4. Rollback Strategy

If `validator` fails a checkpoint or `migration_executor` fails partway
through a table:
- Target staging tables are written with `if_exists="replace"`
  (`workflow/migration_executor.py`), so a failed table load can simply be
  re-run from scratch without manual cleanup — it does not partially
  accumulate rows across retries.
- The **source baseline** Great Expectations checkpoint (`validator.source_baseline`)
  is the rollback reference point: because it runs before any data moves, a
  failed migration can always be diffed against a known-good pre-migration
  state.
- No destructive operation is ever run against the source database — this
  pipeline is read-only on the source side by design, which is itself the
  simplest possible rollback guarantee.
- The dbt marts layer (`validation/generate_dbt_models.py` output) is
  regenerated from `transformation_rules.json` on every run and materialized
  as tables via `dbt run` — re-running it after a correction (as happened
  with `txn_st_cd` in this project) fully replaces the affected model with
  no manual intervention needed.

## 5. Where AI Was Not Trusted

Two concrete findings from this run illustrate where confidence scores
alone are not a sufficient safety mechanism:

1. **Low confidence correctly caught a real problem** (`txn_st_cd`, section 3)
   — this is the gate working as intended.

2. **High confidence did NOT catch a real problem.**
   `insurance_plans.plan_typ_cd` scored 0.85 — above the 0.80 threshold —
   and was never routed to a human. Its generated logic
   (`CASE plan_typ_cd WHEN 'H' THEN 'HMO' WHEN 'P' THEN 'PPO' WHEN 'M' THEN 'MEDICARE_MEDICAID' ELSE 'UNKNOWN' END`)
   has no branch for `'X'`, the code used for self-pay plans in the seed
   schema — every self-pay patient's plan type silently becomes `UNKNOWN`
   in the migrated data. This was caught only by manually reading the
   generated data dictionary against the known seed schema, not by any
   automated gate in this pipeline.

**Conclusion:** confidence-based review is necessary but not sufficient.
A production version of this pipeline should also validate generated CASE
statements against the *full* observed value set for a column (which
`schema_profiler` already captures as `cardinality` and `sample_values`)
rather than trusting the LLM's confidence score alone — e.g., a rule that
doesn't have an explicit branch for every distinct value seen in profiling
should be flagged regardless of the stated confidence.
